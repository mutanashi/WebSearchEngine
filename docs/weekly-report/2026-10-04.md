**一個 shard 失敗，可能拖垮同組其他 shard（coverage 管線）**

[`Metric/Measure/CrawlerAllMetricMeasure.py#L96-L109`](https://github.com/mutanashi/WebSearchEngine/blob/e04dbf7cef357210d064f032b36b120748dbffc3/Metric/Measure/CrawlerAllMetricMeasure.py#L96-L109)：一組 17 個 shard（`256 // 16 + 1`）共用同一個 session；`except` 只印字串，**沒有 rollback**
```python
with self.crawlerDB.session() as session:
    for i in shard_ids:                      # 一組 17 個 shard
        try:
            # ...
            for url, crawled in session.execute(stmt).all():
                found_data.append((url, bool(crawled), False, i))
        except Exception:
            print("[Error] scan url_state_current failed")   # 沒有 session.rollback()
```
PostgreSQL 的 transaction 只要有一句 SQL 出錯，就會進入 aborted 狀態，之後每一句都會被拒絕（`current transaction is aborted, commands ignored until end of transaction block`），直到 rollback 為止。所以只要一個 shard 發生 DB 端的錯誤（表不存在、連線中斷等），**同組排在它後面的 shard 也會全部失敗**，最多少掉約 1/16（6.6%）的 golden URL。（讀程式碼推論，尚未重現。）

**影響**

| | 管線 A：`crawler_stat_*`（Overview） | 管線 B：coverage |
|---|---|---|
| 失敗時 | 該 shard 的 discovered / crawled 當成 0 | 該 shard（和同組後續 shard）的 golden URL 全部判為沒發現、沒爬到，並寫回 `metric_url.is_*` |
| 少掉多少 | 平均 1/256，但 shard 大小差很多（crawler 端報告提到差距曾達 88 倍，整理後約 11 倍），遇到大 shard 會少好幾個百分點 | 最多約 1/16 |
| 錯誤會不會留下來 | 每小時 UPSERT 覆蓋，只有當天最後一次（23:00）失敗才會留下錯的值 | 會。coverage 只在 `--create` 時量一次，那個 batch 的數字會一直是錯的 |
| shard 之間互相影響 | 不會，每個 shard 各用一個 session | 會（見上） |

另外，`_scan_domain_shard` 失敗時，所有找不到 shard 的 URL 都分不到 A / B 隊，A + B 會小於 Total。

dump 驗證：`crawler_stat_total` 的每日值中，**沒有任何一天** discovered 和 crawled 同時比前一天低，所以存下來的值看不出 shard 失敗的跡象。但每小時的中間值沒有存，coverage 也沒有 log 可查，**無法判斷過去有沒有發生過**。

**建議解法**：共同原則是失敗要**看得見**、**不寫假值**、**記錄失敗次數**。
- 4-A：`rawData` 是空的就不建 batch，直接以非 0 結束（讓 cron log 看得到）；`readData` 用快取前檢查 `meta_total_queries > 0`，空 batch 不當快取。
- 4-B：`getQuery` 最後一次失敗時丟例外，呼叫端跳過該 keyword（不 tag、不 commit），並統計失敗數；失敗比例超過門檻就讓整次 `--create` 失敗。
- 4-C：改用 `logging`，記錄 shard 編號與例外內容；設 `statement_timeout`；失敗重試；仍失敗就**不寫入**（或該欄位寫 NULL），並記錄 `failed_shards`。log 要寫到有掛 volume 的位置。
- 4-C（連帶失敗）：`_scan_url_shard` 的 `except` 裡先 `session.rollback()`，或改成每個 shard 各開一個 session（和 `_scan_shard` 一樣），讓一個 shard 的錯誤不會影響同組其他 shard。

### C. 分散式 / 資料保留 / 成本

#### 12. ⚠️ 【分散式必看】read-modify-write 會造成 lost update（[§5.2](#s5-2)、[§8.5](#s8-5)）

**建議解法**
- 能在 DB 內一次完成的就不要「先讀再寫」：
  - `meta_tag_stats = meta_tag_stats || jsonb_build_object('head', ...)`

- 架構上規定：`--create` 和每小時的 `status` 只由一台主機負責，其他主機只做別的 measure。
- 「最新 batch」統一一種定義（`id` 或 `created_at` 擇一）。

### §2.3 空 batch（batch 10~17）

| batch id | created_at | meta_total_queries |
|---|---|---|
| 9 | 2026-06-12 14:00 | 10,003 |

<a id="s2-7"></a>
### §2.7 SerpApi 失敗 vs rollback

rollback 只在**丟出例外**時發生（DB 錯誤、程式 bug、連線中斷）。SerpApi 失敗不會丟例外，只回傳 `[]`，所以結果**會被 commit**。

| 階段 | commit 粒度 | 中途出例外的結果 |
|---|---|---|
| `_save_to_database` | 最後 commit 1 次 | 全空：batch 和 query 都不留 |
| `getGoldenSet` | **每個 keyword commit 1 次** | 已完成的 keyword 保留；`_update_batch_stats` 沒跑 → `meta_tag_stats` 過時 |
| `CrawlerAllMetricMeasure` | 最後 commit 1 次 | 全空：`metric_url` 狀態不更新、coverage 不寫 |
| `CrawlerStatusMeasure` | 最後 commit 1 次 | 全空：Total / A / B 三列都不寫 |

SerpApi 搜尋失敗 → 該 query 照樣加上 tag、0 個 URL，並被 commit。dump 中共有 **1,416 個**這種 query：batch 1 有 364 個、batch 5 有 23 個、batch 9 有 1,029 個（推測當時額度用完）。

重跑同一個 batch 時：先 `DELETE` 舊 URL → SerpApi 失敗回傳 `[]` → 插入 0 筆 → commit → 原本的 URL 和 `is_*` 狀態被永久刪除（#5）。

<a id="s4-4"></a>
### §4.4 重跑 random 會越選越多

- 每次重跑 random 都會用 `random.sample` 再抽一批不同的 keyword，加上 `"random"` tag，但**不會移除上一次的 tag**。
- dump 證據：batch 1 的 random query 有 **1,313 個**（> N = 1000），`meta_tag_stats.random.queries` 也是 1313。
- head 重跑不會有這個問題（每次都選同樣的前 N 名），只是會重抓 URL。

<a id="s5-2"></a>
### §5.2 read-modify-write

```python
current_stats = dict(batch.meta_tag_stats)             # 1. 讀出來
current_stats['head'] = {"queries": ..., "urls": ...}  # 2. 在 Python 改
batch.meta_tag_stats = current_stats                   # 3. 整個寫回
```
兩台主機（或 head 和 random）**同時**跑時，兩邊都讀到舊值，各自寫回 → 後寫的蓋掉先寫的（lost update）。目前 head 和 random 分開時段跑，所以還沒出事；改成分散式就會出事。

對照：用 `meta_tag_stats || jsonb_build_object(...)` 在 DB 內一次完成，就不會有這個問題。

<a id="s6-4"></a>
### §6.4 shard 查詢失敗與 log

| 位置 | 失敗時的行為 |
|---|---|
| `CrawlerStatusMeasure._scan_shard` | 回傳 0，**完全沒有 log** |
| `CrawlerAllMetricMeasure._scan_url_shard` / `_scan_domain_shard` | 只印固定字串，沒有 shard 編號，也沒有例外內容 |
| `_load_indexed_urls`（selectdb） | 沒有 try → 整次 coverage 中止、不寫入 |

- 一個 shard 失敗，總數就少約 1/256，而且每小時的 UPSERT 會把當天先前的正確值蓋掉。
- 整個 repo 沒有用 `logging`；cron 把輸出導到容器內的 `/var/log/cron.log`，容器重建就會消失。
- 判讀方法：shard 失敗時 discovered 和 crawled 會**同時**下降、之後回升（V 字缺口）。crawler 修剪 URL 時只有 discovered 下降，crawled 照樣上升（例：2026-05-24 discovered −20%、crawled 上升，是刻意修剪）。
- 可能的原因：修剪時表被替換或鎖住、磁碟滿（1TB）、整點多個 cron 同時跑導致連線數不足、schema 或權限變更、連線中斷。

### §7.4 crawler_stat 的 fetch 欄位

<a id="s7-4-a"></a>
**(a) daily 系統性低估約 4%**
對 95 個「前 7 天都有資料」的日子，比較 `fetch_ok_7` 和「存下來的 7 個 daily 加總」：weekly 一律比較大，差距中位數 **3.5%**（0 ~ 4.7%）。
原因：最後一次寫入是 23:00，存下來的 daily 少了最後 1 小時（1/24 ≈ 4.2%）；weekly 則是當下從 `summary_daily` 重算，前幾天都是完整的。

<a id="s7-4-b"></a>
**(b) 2026-06-04 ~ 08-07：crawler 停機，但 measure 還在跑**

| 日期 | discovered | fetch_ok | fetch_ok_7 |
|---|---|---|---|
| 06-04 | 5,056,751,243 | 29,367,333 | 193M |
| 06-05 | 5,056,751,243（不變） | 963,809 | 166M |
| 06-06 | 5,056,751,243（不變） | **NULL** | 136M ↓ |
| … 08-07 | 5,056,751,243（不變） | NULL | … |

- discovered / crawled 63 天完全不變 → crawler 沒在跑。
- `fetch_ok` 是 NULL：`summary_daily` 沒有當天的列 → dict 裡沒有這個 key → UPSERT 沒提供 → NULL。
- `fetch_total` 卻是 **0**：`day_total = stats_data["fetch_total"]` 讀取 `defaultdict(int)` 時會**自動建立 key = 0**。同一列裡「沒資料」有的寫 NULL、有的寫 0。
- weekly / monthly 逐日滑落到 0，圖上看起來像「爬得越來越少」，其實是停機。

<a id="s7-4-c"></a>
**(c) A / B 的 fetch 欄位全寫 0**
`summary_daily` 是全域資料，沒有 shard，所以程式直接填 0。但 crawlerdb 的 `domain_stats_daily` 每個網域每天一列，**有 `shard_id`**，可以分隊計算：
```sql
SELECT CASE WHEN shard_id < 128 THEN 'A' ELSE 'B' END AS team,
       SUM(num_fetch_ok) FILTER (WHERE event_date = CURRENT_DATE)      AS fetch_ok,
       SUM(num_fetch_ok) FILTER (WHERE event_date >= CURRENT_DATE - 6) AS fetch_ok_7
FROM domain_stats_daily
WHERE event_date >= CURRENT_DATE - 29
GROUP BY 1;
```
（待確認：`domain_stats_daily` 的加總是否等於 `summary_daily`。）

<a id="s8-3"></a>
### §8.3 一天之內：最後寫的贏

`status` 每個整點跑一次，`stat_date` 是主鍵，所以一天只有一列：

| 時間 | 動作 |
|---|---|
| 00:00 | 當天還沒有列 → INSERT |
| 01:00 ~ 22:00 | 每次都 UPDATE，整列被蓋掉 |
| 23:00 | 最後一次寫入 = 存下來的值（所以少最後 1 小時 → [§7.4 (a)](#s7-4-a)） |

dump 證據：最新一列 `2026-10-01` 的 `fetch_ok` = 3,526,448，前幾天都是 2,000~2,800 萬，只有正常的約 13% → dump 是 10-01 凌晨拿的，這一列**還沒寫完**。
→ dashboard 最右邊那一點（今天）的 flow 值一定偏低，不能拿來和前幾天比。

<a id="s8-5"></a>
### §8.5 UPSERT 的「最後寫的贏」什麼時候會出錯

1. 23:00 那次剛好有 shard 失敗 → 偏小的值蓋掉 22:00 的正確值。
2. 改成分散式後，多台主機都跑 `status` → 比較慢的那台用**比較舊的快照**蓋掉新的，而且 256 個 shard 會被重複掃描。

PostgreSQL 可以在 `DO UPDATE` 後面加條件，條件不成立就不更新：
```sql
ON CONFLICT (stat_date) DO UPDATE
SET fetch_ok = EXCLUDED.fetch_ok, ...
WHERE EXCLUDED.fetch_ok >= crawler_stat_total.fetch_ok;  -- 當天的 fetch_ok 只增不減
```
這個條件不能用在 discovered，因為修剪會讓它合理地下降。比較通用的做法是加 `measured_at` 欄位，只讓較新的快照覆蓋。

### §附錄 C.4 URL 逐字比對

- 去重和比對的單位都是「**完全相同的 URL 字串**」。同一頁的不同寫法（`http` / `https`、有沒有 `www.`、結尾 `/`、大小寫、`utm_` / `#`）都會被當成不同的 URL。
- dump 證據：同一頁不同寫法共 **47 組**，其中 **18 組** discovered 一個 t、一個 f，而且 `shard_id` 相同：
  - `instagram.com/banksy/` t vs `instagram.com/Banksy/` f（大小寫）
  - `vancouverattractions.com/` t vs `www.vancouverattractions.com/` f（www）
  - `mdr.de/in-aller-freundschaft` t vs `mdr.de/In-aller-freundschaft` f（大小寫）
  - 差異類型：大小寫 19、www 11、結尾 `/` 7、http/https 5、`#` / utm 5
- 看得到的只是冰山一角：golden set 只出現一種寫法時，看不出 crawler 存的是哪一種 → 實際低估多少未知。
- 影響範圍：只有 coverage 管線（比對 crawlerdb `url_state` 和 selectdb `selected_urls_current`）。Overview 只做 `COUNT(*)`，不受影響。golden set 這邊同一頁兩種寫法會算成 2 個 URL → 分母多算。
- 其他細節：
  - 只在同一 batch、同一 tag 內去重，head 和 random 各算各的。
  - 每個 URL 權重都是 1，和 Google 名次、query frequency 無關。
  - `metric_url.is_*` 是最後一次量測的快照，舊 batch 不會再被更新。

<a id="sE"></a>
### §附錄 E rank 指標的演算法方向

漏斗：`golden URL → discovered → crawled → indexed → ranked（出現在我們搜尋結果的前 K 名）`

- 如果只報 `ranked / total`，數字低時分不出是排序不好、還是根本沒爬到。所以同時報兩個：
  - `ranked / total`：端到端
  - **`ranked / indexed`**：純排序能力

| 指標 | 定義 | 優點 | 缺點 |
|---|---|---|---|
| **Recall@K** | 前 K 名命中的 golden URL 數 ÷ golden URL 數 | 簡單、好解釋 | 不看名次 |
| Hit@K | 前 K 名至少命中 1 個的 query 比例 | 貼近使用者感受 | 太粗 |
| MRR | 1 ÷ 第一個命中的名次，取平均 | 看「多快找到」 | 只看第一個 |
| **NDCG@10** | 用 Google 名次當相關度 | 名次越前越重要；業界標準 | 把 Google 當正解 |
| RBO | 比較兩份排序清單，越前面權重越大 | 專門比較兩個搜尋引擎的排序 | 較難解釋 |

- 建議組合：dashboard 用 **Recall@10**；分析用**以 indexed 為條件的 NDCG@10**（IDCG 只用有被 index 的 golden URL 計算），把覆蓋率和排序分開。
- 前置條件：先處理 #1（URL normalize）、#3（gl / hl）；量測時間要接近 SerpApi 抓取時間；head / random 分開報。
- 資料表：`metric_url` 加 `our_rank`（在我們搜尋結果中的名次，沒出現就是 NULL）；可另建 `metric_query_rank(query_id, stat_date, recall_10, ndcg_10, mrr)`。
- 限制：Google 不是絕對正解，這些指標量的是「和 Google 的一致程度」。我們的 index 遠小於 Google，端到端的數字預期會很低，所以一定要搭配條件版本一起看。
